# Foody API v2 — контракт для фронтенда

> Все ручки с префиксом `/api/v1/`
> Swagger: `GET /api/docs/` · схема OpenAPI: `GET /api/schema/`

---

## Что нужно знать до чтения

Три вещи определяют весь контракт, и без них он выглядит странно.

**Позиция — это блюдо в конкретном заведении.** К ней привязаны все посты про него,
её рейтинг и её цена. В коде `MenuItem`, в интерфейсе «позиция» или «блюдо».

**До одобрения модератором в каталоге не появляется ничего.** Пост несёт «заявку
на размещение» — данные, по которым заведение и позиция будут созданы при одобрении.
Поэтому у неодобренного поста `menu_item = null`.

**Оценка в посте — это оценка блюда автором**, а не оценка поста посторонними.
Из этих оценок и складывается рейтинг позиции, по одному голосу с человека.

---

## Доступ

| Что | Кто может |
|---|---|
| Лента, посты, позиции, заведения, справочники, поиск по каталогу | **все, без входа** |
| Создание постов, лайки, сохранения, комментарии, подписки, подсказки заведений | вошедшие |
| Модерация | сотрудники (`is_staff`) |

Авторизация — `Authorization: Bearer <access>`. Токен по `POST /auth/token/`
(вход **по email**).

Вход закрыт, пока не подтверждена почта: в этом случае `POST /auth/token/`
отвечает **403** с телом `{"detail": "…", "code": "email_not_verified"}`.
Признак `code` отличает этот случай от неверного пароля (401) — вести нужно
на ввод кода, а не показывать «неверный пароль».

## 1. Лента и посты

### `GET /posts/`

Фильтры:

| Параметр | Значения | Что делает |
|---|---|---|
| `feed` | `subscriptions` \| `saved` | только подписки / только сохранённое |
| `ordering` | `popular` | по лайкам; по умолчанию по свежести |
| `author` | id | посты одного человека |
| `menu_item` | id | посты про одно блюдо |
| `search` | текст | по названию блюда, заведению, типу блюда, тегам и описанию |
| `tag_name` | имя тега | переход по «#тег»; решётка в начале срезается |
| `category_id` | id таксона | по категории позиции, любая из четырёх осей |
| `price_min`, `price_max` | число | по цене позиции; негодное значение игнорируется |
| `page` | число | страница |

Фильтры применяются **после** правил видимости, поэтому через них нельзя
достать чужой пост на модерации.

**Лента и поиск разделены по городам.** Вошедшему показываются посты тех, у кого
на момент публикации стоял его нынешний город (`city` в профиле). Город поста —
снимок: автор переехал, а старые посты остались у прежнего города. Написания
приводятся к одному ключу, «Ростов-на-Дону» = «ростов на дону».

По городу **не** сужаются: `?author=`, `?menu_item=`, `?feed=saved` и прямая
ссылка `/posts/{id}/` — там смотрят на конкретное. Гость и тот, у кого город
не указан, видят все города.

Гость видит только одобренные посты. Автор дополнительно видит свои —
на модерации и отклонённые. Чужие неодобренные не видны никому.

```json
{
  "count": 42, "next": "...", "previous": null,
  "results": [{
    "id": 12,
    "user": {"id": 3, "username": "alice", "full_name": "Алиса", "avatar": "/media/…"},
    "menu_item": {
      "id": 7, "name": "Чизбургер",
      "restaurant": {"id": 2, "name": "Бургерная", "address": "Тверская 15",
                     "city": "Москва", "is_closed": false,
                     "posts_count": 24, "contributors_count": 9, "is_confirmed": true},
      "dish_type": "Бургер",
      "taxons": [{"id": 5, "kind": "cuisine", "name": "Американская", "slug": "american"}],
      "price": "350.00", "price_confirmed_at": "2026-08-01T10:00:00Z",
      "rating_raw": 8.4, "ratings_count": 12, "posts_count": 15
    },
    "description": "очень вкусно", "size": "0.4 л",
    "author_rating": 9.0,
    "images": [{"id": 1, "image": "/media/post_images/…", "uploaded_at": "…"}],
    "statistics": {"likes_count": 10, "saves_count": 3, "comments_count": 2},
    "tags": [{"id": 1, "name": "сочно"}],
    "created_at": "2026-08-12T09:00:00Z", "city": "Москва",
    "status": "approved", "rejection_reason": "",
    "is_liked": false, "is_saved": false, "is_editable": false
  }]
}
```

`is_editable` — **одобренный пост не редактируется**, его можно только удалить.
Править можно посты на модерации и отклонённые.

### `POST /posts/` — создание

`multipart/form-data`. Две развилки: позиция и заведение либо выбираются
из существующих, либо создаются.

**Позиция уже есть:**

| Поле | |
|---|---|
| `menu_item_id` | id позиции |
| `price` | необязательно — заявка «цена изменилась» |

Тип блюда и категории передавать нельзя: они берутся с позиции.

**Позиция новая:**

| Поле | |
|---|---|
| `menu_item_name` | название блюда |
| `dish_type_id` | тип блюда из справочника — обязателен |
| `taxon_ids` | категории (повторяющееся поле) |
| `price` | **обязательна** — станет ценой позиции |

**Заведение** — либо `restaurant_id` из подсказок, либо все три поля сразу:
`restaurant_name`, `restaurant_address`, `restaurant_city`. Половинчатый ввод
не принимается: без адреса заведение не отличить от тёзки на другой улице.

**Общее:** `author_rating` (0–10, обязательно), `description`, `size`,
`tags_list` (до 10), `uploaded_images` (до 10 файлов, по 10 МБ).

Город поста не передаётся — он берётся из профиля автора. **Без города в профиле
пост не создастся** (`400`): он не попал бы ни в одну городскую ленту.

Лимит — 100 постов в сутки; удалённые тоже считаются.

Ответ `201` — созданный пост в формате ленты, со `status: "pending"`.

### `PATCH /posts/{id}/`, `DELETE /posts/{id}/`

Правка возвращает пост на модерацию. Одобренный отдаёт `403`.
Удаление мягкое: запись остаётся в базе, из выдачи пропадает.

Чужой неодобренный пост отдаёт `404`, а не `403` — посторонний не должен
узнать даже о его существовании.

## 2. Вовлечённость

| Ручка | |
|---|---|
| `POST/DELETE /posts/{id}/like/` | лайк |
| `POST/DELETE /posts/{id}/save/` | сохранение |
| `POST/DELETE /comments/{id}/like/` | лайк комментария |

Ответ: `{"active": true, "count": 11}` — новое состояние и счётчик, перезапрашивать
пост не нужно. Повторный `POST` дубля не создаёт.

`GET /comments/?post=<id>` — **только корневые** комментарии, у каждого
`replies_count`. Ветка ответов запрашивается отдельно: `GET /comments/?parent=<id>`.
Так длинная переписка под одним комментарием не растягивает общий список.

`POST /comments/` — `{post, text}`, для ответа добавляется `parent`. Ветка
одноуровневая: ответ на ответ бэкенд сам прикрепляет к корню, вглубь дерево
не растёт. У ответа есть `reply_to` — логин того, кому отвечают.

`DELETE /comments/{id}/` — удаление мягкое, править может только автор.
Счётчик комментариев поста считает и ответы.

## 3. Каталог

### `GET /menu-items/`

Ручка страницы поиска: **вкладка поиска ищет позиции, а не посты**.

| Параметр | |
|---|---|
| `search` | умный поиск по названию: опечатки, раскладка, латиница, синонимы |
| `category_id` | id таксона любой из осей |
| `price_min`, `price_max` | по цене позиции |
| `cuisine` | слаги кухонь через запятую — «или» |
| `type` | слаги видов через запятую — «и» |
| `dish_type` | тип блюда по названию |
| `restaurant` | позиции одного заведения |

Категории позиции проставляются **из типа блюда**, если автор не выбрал свои:
«Роллы» — это японская кухня, суши и ресторан. Позиция без категорий не нашлась
бы ни одним фильтром, поэтому клиенту это не доверено.

**Осей две: кухня и вид.** Формат, форма и особенности слиты в «вид» — делить
«фастфуд», «бургеры» и «веганское» по трём осям значило бы заставлять человека
угадывать, где лежит нужное.

Значения ведут себя по-разному, и это следует из данных: кухня у позиции одна,
поэтому `?cuisine=japanese,italian` — это «или». Видов у позиции сколько угодно,
поэтому `?type=fastfood,vegan` — это «и», то есть веганский фастфуд.

Поиск применяется **после** фильтров: ищем внутри того, что и так показали бы.

**Выдача ограничена городом смотрящего** (по городу заведения), как и лента.
Исключение — `?restaurant=`: туда приходят по ссылке. Гость и тот, у кого город
не указан, видят все города.

В выдаче только позиции с хотя бы одним видимым постом.

### `GET /menu-items/search/?text=…` — умный поиск

Понимает опечатки, слитное написание, латиницу и неверную раскладку:
`чиз бургир`, `чизбургер`, `chiz burger`, `xbp ,ehuth` — всё находит «Чиз Бургер».

Ищет и среди позиций **без постов**: иначе человек не найдёт вчера созданную
и заведёт дубль. Поэтому ручка только для вошедших.

### `GET /menu-items/{id}/` — карточка блюда

К полям позиции добавляются:

```json
{
  "tags": [{"id": 1, "name": "сочно", "mentions": 4}],
  "brand_rating": {"rating_raw": 8.1, "rating": 7.9,
                   "ratings_count": 340, "restaurants_count": 12}
}
```

`tags` — только те, что написали **двое разных** людей.
`brand_rating` — рейтинг блюда по всей сети, `null` у несетевых.

Карточка и её посты открываются по прямой ссылке **из любого города** — городом
сужается только список `/menu-items/`. Присланная ссылка должна открываться.

Показывать пользователю надо `rating_raw` и «по N оценкам», а сортировать
каталог — по `rating`: иначе непонятно, почему единственная оценка 10/10
отображается как 6.2.

### `GET /menu-items/{id}/posts/`, `GET /restaurants/{id}/`, `GET /restaurants/{id}/menu/`

У позиции есть `photo` — снимок с самого свежего одобренного поста о ней.
Своих картинок у позиции нет, поле считается подзапросом при выдаче списка.

В **списке** `/restaurants/` только подтверждённые — те, о которых написали двое
разных. По прямой ссылке `/restaurants/{id}/` заведение открывается с первого
поста: на него ведёт карточка уже опубликованного поста. Скрытые модератором
(`is_hidden`) не отдаются нигде.

## 4. Справочники и заведения

`GET /dish-types/` — типы блюд с категориями по умолчанию. Из них форма создания
поста подставляет категории при выборе типа.

`GET /taxons/?kind=cuisine|type` — категории по осям.

### `GET /places/suggest/?text=…&city=…` — подсказки заведений

Главная защита от дублей. Ищет нечётко и по синонимам — написаниям, под которыми
это место уже пытались завести.

```json
[{"id": 2, "name": "Кофемания", "address": "ул. Пушкина, д. 10", "city": "Москва",
  "posts_count": 24, "contributors_count": 9, "is_confirmed": true}]
```

`posts_count` в интерфейсе обязателен: рядом с «Кофемания · 24 поста» дубль
с одним постом никто не выберет.

`POST /places/not-found/` (`{query, comment}`) — «не нашёл своё место».

## 5. Модерация (только сотрудники)

`GET /moderation/?kind=new_items|existing_items|price_changes|suspicious`

Подозрительные посты идут первыми. По каждому:

```json
{
  "will_create": {
    "restaurant": {"id": null, "name": "Кафе Кофемания", "address": "Пушкина 10",
                   "city": "Москва", "is_new": true, "posts_count": 0},
    "menu_item": {"name": "Латте", "dish_type": "Латте", "taxons": [], "price": "250.00"}
  },
  "similar_restaurants": [{"id": 2, "name": "Кофемания", "address": "ул. Пушкина, д. 10",
                           "posts_count": 24, "similarity": 0.71}],
  "similar_menu_items": [{"id": 7, "name": "Латте", "similarity": 0.9}],
  "price_change": {"current": "200.00", "proposed": "250.00"},
  "warnings": ["Похожее заведение уже есть, а автор создаёт новое"],
  "possible_duplicate": true, "looks_suspicious": false
}
```

`similar_restaurants` сервер ищет **сам**, независимо от того, показывал ли фронт
подсказки: обойти интерфейс через любой HTTP-клиент — дело двух минут.

`GET /moderation/stats/` — счётчики очереди, включая `suspicious`
и `waiting_over_day`.

`POST /moderation/{id}/approve/` — тело необязательное:

| Поле | |
|---|---|
| `menu_item_id` | привязать к существующей позиции вместо создания новой |
| `menu_item_name` | поправленное название |
| `accept_price` | по умолчанию `true` |

Поля решения: `menu_item_id` — привязать к существующей позиции, `restaurant_id` —
опознать заведение (блюдо новое, а место уже в каталоге), `menu_item_name` —
поправленное название, `accept_price` — решение по цене.

Написание автора при опознании места сохраняется синонимом, поэтому следующий
такой пост подсказки приведут в это же заведение сами.

**Решение по цене отдельно от решения по посту:** хороший пост с бредовой ценой
публикуется, а цена отклоняется.

`POST /moderation/{id}/reject/` — `{reason}`, причину увидит автор.

## 6. Пользователи

`POST /users/register/`, `GET/PATCH /users/me/`, `GET /users/{id}/`,
`POST/DELETE /users/{id}/subscribe/`.

### Подтверждение почты и сброс пароля

Регистрация создаёт пользователя и отправляет на указанный адрес код из шести
цифр. Пока код не введён, войти нельзя.

| Ручка | Тело | Ответ |
|---|---|---|
| `POST /users/email/verify/` | `{email, code}` | `{access, refresh}` — подтверждает почту и сразу пускает внутрь |
| `POST /users/email/resend/` | `{email}` | отправляет код заново |
| `POST /users/password/reset/` | `{email}` | отправляет код для смены пароля |
| `POST /users/password/reset/confirm/` | `{email, code, password, password_confirm}` | `{access, refresh}` — меняет пароль и пускает внутрь |

Про ответы этих ручек важно знать три вещи:

- **Отправка кода отвечает одинаково** независимо от того, есть такой адрес в
  базе или нет: `200 {"detail": "Если такой адрес есть, мы отправили на него
  код."}`. Иначе форма восстановления превращается в способ выяснять, кто
  зарегистрирован в сервисе. По той же причине неверный код и несуществующий
  адрес дают один и тот же текст «Неверный или устаревший код.».
- **Между письмами есть пауза** (по умолчанию минута). Если попросить раньше,
  придёт `429` с `retry_after` — сколько секунд осталось. Это число удобно
  показывать на кнопке «отправить ещё раз».
- **Код одноразовый**, живёт 15 минут и терпит 5 неверных попыток. После этого
  нужен новый — даже верный старый код уже не подойдёт.

`GET /users/{id}/following/` — на кого подписан, `GET /users/{id}/followers/` —
кто подписан на него. Оба списка пагинированы и отдают тот же объект, что
`/users/{id}/`, включая `is_following` для текущего пользователя — кнопку
подписки можно рисовать прямо в списке.

## 7. Общее

**Пагинация** — везде `count / next / previous / results`, размер из `PAGE_SIZE`.

**Ошибки** — DRF-формат: `{"detail": "…"}` либо `{"поле": ["…"]}`.
`401` — нужен вход, `403` — нет прав, `404` — нет или не видно.

**Частота запросов** — 60/мин для анонимов, 300/мин для вошедших,
10/мин на вход.
